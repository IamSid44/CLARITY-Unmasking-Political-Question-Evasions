### The card is genuinely shared, and only one of two is visible

`nvidia-smi` reports **two** RTX PRO 6000 Blackwell cards, but the shell environment sets
**`CUDA_VISIBLE_DEVICES=0`**, so torch sees exactly one device. This is the correct one to
have: GPU 1 is at 90.5 / 97.9 GB under a resident `VLLM::EngineCore` process and would be
useless to us anyway.

Consequences, and they are binding:

- The 50 GB budget in CLAUDE.md invariant 5 is **not theoretical**. At check time a
  concurrent job held 26.9 GB of the 95 GB card, leaving 68.1 GB. That headroom can shrink
  without warning.
- Every training script must take `--max-vram-gb`, log peak allocated memory, and **fail
  fast rather than OOM a card someone else is using**.
- Do **not** unset or widen `CUDA_VISIBLE_DEVICES`. GPU 0 is the correct and only target.
- The Phase 3.2 plan (Qwen3-14B LoRA bf16, ~35 GB peak) fits inside 68 GB with room, but the
  playbook's fallback rule stands: **if free VRAM is below 40 GB at launch, drop to Qwen3-8B
  and log that the fallback was taken.**

### Version pins that had to change

**None.** No package was downgraded. This was checked explicitly, because `peft` and
`accelerate` resolving against `transformers` 5.x carried a real risk of pip silently
backtracking `transformers` down to the 4.x line. Before and after the install,
`transformers` is 5.17.0 and `torch` is 2.11.0+cu128. Nothing moved.

### Deviations from the playbook

1. **Python 3.12.3, not 3.11.** Used the existing venv rather than building a new 3.11 one.
   The stack that matters (torch 2.11.0+cu128 on sm_120) is already correct, and rebuilding
   it risked landing on a worse combination for no benefit. No 3.11-specific requirement
   exists anywhere in the plan.
2. **`transformers` is on the 5.x line, not 4.x.** The playbook was written against >= 4.48,
   which 5.17.0 satisfies numerically, but v5 is a major release with real API drift.
   **Risk carried forward to Phase 3.1:** encoder training code must be written against the
   5.x API and smoke-tested for one step before any 5-seed sweep is launched. Do not copy
   4.x-era `Trainer` examples.

## Attention backends

The playbook's Blackwell warning is confirmed correct in principle and unexercised in
practice: this is an **sm_120** card, so **FlashAttention-4 will not run on it** — consumer
and workstation Blackwell lack the TMEM subsystem FA4 requires; only sm_100/sm_103
(B200/B300) get FA4.

| Backend | Status |
|---|---|
| `flash_attn` | not installed |
| `flashinfer` | not installed |
| `xformers` | not installed |
| **torch SDPA** | **available** (math / mem-efficient / flash) |

Currently **torch's built-in SDPA is the only attention backend**, which is a safe and
sufficient default for Phase 3 encoder training. If throughput becomes the binding
constraint, install FA2 (**not** FA4) or FlashInfer, and set `VLLM_FLASH_ATTN_VERSION=2` for
any vLLM serving in Phase 7/8. Per the playbook, vLLM is deliberately **not** installed yet.

Some builds may additionally need `TORCH_CUDA_ARCH_LIST="12.0"`; not required so far.

## bitsandbytes 4-bit viability

Verified live, not just imported: `bnb.nn.Linear4bit(64, 64, compute_dtype=bfloat16)` was
constructed on CUDA and a forward pass ran, returning shape `(2, 64)`. **4-bit quantization
works on this sm_120 card.**

This only enables the QLoRA *fallback* path. Per the playbook the primary Phase 3.2 system is
**LoRA in bf16, deliberately unquantized**, so that quantization does not confound the
controlled comparison against the factorized model.
